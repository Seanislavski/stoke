## Static Assets, Hosted Docs & Launch (06/23–07/01/2026)
> Launch post-mortem, funnel analysis + Discord announcement history archived in `docs/claude-md-archive/2026-07-26-narrative-archive.md` and `2026-07-28-narrative-archive.md`.
- **⚠️ The middleware matcher must exclude EVERY hosted static file extension.** `config.matcher` originally excluded only image types, so `.pdf`/`.html` in `apps/web/public/` hit the auth gate and redirected logged-out visitors to `/login`. Now excludes `pdf|html|ico|txt|xml|webmanifest`. **Any new public static file type must be added there.**
- **⚠️ ALWAYS test hosted assets while LOGGED OUT, and check content markers not just status.** The login shell also returns 200 `text/html` (~13–23KB) with no `type=password` in the source (client-rendered form) — trivially mistaken for success. Verify `%PDF-` magic bytes for PDFs; for pages, look for real content markers.
- **PDF from HTML** (zero deps): headless Chrome/Edge print-to-pdf — see the elevated-terminal `--do-not-de-elevate` gotcha in the global CLAUDE.md, which is what silently breaks it.

## Off-Platform Library Export & Backup (09/09–09/10/2026 — `47c0459`, `dfea8fc`, `5631aef`)
> **Why it exists, in Sean's words:** the actions he is taking about an unstable world are *"to build Stoke as a resource - a library of sorts"*. The library lived in ONE Supabase project, ONE Railway deploy, ONE account. **★ That is resilient against people forgetting things; it is not resilient against the infrastructure going away.** The export needs nothing from Stoke, Supabase or Railway to stay readable.
- **`scripts/export-library.mjs`** — read-only, follows the established `scripts/` pattern (service key parsed out of `apps/web/.env.local`, run from repo root, same as `library-shape.mjs`). Writes `index.md` (the entry point for a human who finds the folder with no context) + `questions/NNN-slug.md` per question + `library.json` (structure intact, for re-import). Flags: `--slug` (default `bodydoublingcom`), `--out`, `--photos`.
- **SCOPE + PRIVACY were Sean's calls, not defaults:** Q&A library **only** (not bulletin/events, not a full DB dump), and **published content only, attributed by display name or username** — no emails, no user IDs, no pending or rejected content. **Rationale worth keeping:** archiving what mods chose *not* to publish would make the export itself sensitive, and full anonymisation would destroy the credit `publishExistingQuestion` deliberately preserves by never touching `asker_id`.
- **⚠️ `kb_answers.attribution` MUST WIN over the profile lookup.** Unclaimed Discord captures are authored by `SILAS_USER_ID`, so a profile-only lookup credits the bot instead of the human. Same trap as the QotW congrats bug.
- Reminder: `profiles.id` is the PK the `kb_*` tables reference, **not** `profiles.user_id`.
- **Weekly backup: `scripts/backup-library.cmd`** + Windows scheduled task **`Stoke library backup`** (Sundays 10:00, `-StartWhenAvailable` so a missed week catches up rather than skipping). Destination `C:\Users\Sean\Proton Drive\seanislavski\My files\library-export`. Every run appends timestamp + output + `RESULT: OK`/`FAILED` to `_backup-log.txt` beside the backup.
- **★ "It syncs to the cloud" is not the same claim as "it survives losing my account."** The first export landed under OneDrive, which does sync off-laptop — but it is the same Microsoft account that holds everything else Sean owns. Proton is a different provider and a different account, which is the threat actually described. Don't let the first claim stand in for the second.
- **⚠️ KNOWN LIMIT: the only failure signal is a log file nobody opens.** The task reads the Supabase service key from `.env.local`; if that key rotates, the backup fails weekly in silence. Flagged to Sean, not built.
- **⚠️ `library-export/` is gitignored** — member content and a backup artifact, not source.
- **★★ A REPORTING COUNTER MUST NOT LIVE ON THE CODE PATH IT REPORTS ON.** The summary line named a `photos/` folder whenever `--photos` was passed, even though `mkdirSync` only runs when there are photos — it advertised a folder that never existed. The *first* fix gated on `photoJobs.length`, but `photoJobs` is only populated when `--photos` is passed, so a plain run with images present would have printed "(no images in this library)" — a **false negative about the very data the backup exists to preserve.** Fixed with a separate `photosSeen` counter incremented regardless of the flag. Both bugs were in the ACCOUNT of the work, not the work — the failure mode that matters most in a tool meant to run unattended.
- **Verification that actually proved it:** did not trust the script's own summary — counted photos independently by parsing `library.json` in a separate `node -e` (0 and 0, confirming `--photos` was a genuine no-op rather than a silent download failure); and triggered the task through the **scheduler** (`Start-ScheduledTask` → `LastTaskResult: 0`), not just by running the `.cmd` by hand. **The script's output and the script's product are two different witnesses; ask the product.**
- **Current shape (09/10/2026): 21 published questions, 31 answers, 8 categories, 109 KB.** ⚠️ Pull these numbers, never quote them — that's what `library-shape.mjs` is for. **The bottleneck for the library-as-resource goal is VOLUME, not durability**: 14,700 Discord members generate this material daily and Silas already pipes it.
